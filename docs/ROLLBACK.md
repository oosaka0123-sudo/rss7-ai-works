# Rollback Playbook

## 目的

AIによる更新で不具合が発生した場合に、判断を迷わず直前の正常状態へ戻す。

## 原則

- 壊れた変更へ追加修正を重ねる前に、まず影響範囲を止める。
- 正常だったmain commitを基準に戻す。
- 本番公開後に異常が確認された場合は、原因調査より復旧を優先する。
- Secretsや認証情報をログ・Issue・PRへ貼らない。

## GitHub上の基本手順

1. 問題を起こしたPRを特定する。
2. 直前の正常なmain commitを確認する。
3. 問題PRをrevertするPRを作成する。
4. quality / safety checksを通す。
5. マージ後、本番へ限定デプロイする。
6. 本番URLで主要ページを確認する。
7. `PROJECT_STATE.json` の `last_verified_commit` と `last_deploy_check` をActions経由で更新する。

## 自動ロールバックの将来条件

Phase 3以降、次の条件をすべて満たす低リスク変更のみ自動ロールバック対象とする。

- デプロイ前commitが記録されている
- デプロイ対象ファイルが限定されている
- 本番ヘルスチェックが機械判定できる
- DB migrationを含まない
- Secrets、認証、課金、ドメイン変更を含まない

## 人間承認必須

次のロールバックは自動実行しない。

- DB構造変更を伴う
- `.htaccess` / 認証 / 決済 / ドメイン設定を伴う
- 大量ファイル削除を伴う
- 本番状態とGitHubの対応関係が確認できない
